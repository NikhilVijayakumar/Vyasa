## local-index

| Q | Question | Recommended answer |
|---|---|---|
| Q4 | A project disappears. What happens (FR-007 S4)? | It becomes `missing` (path gone) or `inaccessible` (present but unreadable) after one scan. Observations and history stay. Nothing is deleted; retention can mark long-missing projects `archived`. |
| Q7 | How do overlapping refreshes behave (NFD-005)? | One writer at a time through a lock row with owner and heartbeat, on top of WAL and a 5 s busy timeout. A second refresh returns `OPERATION_IN_PROGRESS` and is not queued. A lock whose heartbeat is older than twice the interval can be taken over, and the takeover is recorded. |
| Q13 | How are the proposed performance targets validated (NFD-003/004)? | A seeded synthetic corpus generator for 10, 100, 500, and 1,000 projects in `tests/bench/`, recording p95 for lookup, search, context, and related queries. Targets stay non-blocking until measured and reviewed. |
| Q15 | What do current, stale, partial, and unknown mean? | `current`: last run completed within 24 hours (configurable). `stale`: older. `partial`: the last run was partial or interrupted. `unknown`: never scanned. Queries report this state and never scan. |

## project-identity

| Q | Question | Recommended answer |
|---|---|---|
| Q2 | How are remote URLs normalized (DFR-005)? | Drop scheme, userinfo, default port, a trailing `.git` and slash; convert `git@host:org/repo` and `https://host/org/repo` to `host/org/repo`. Lowercase the whole identity for github.com and bitbucket.org; keep path case for unknown hosts. Use the remote named `origin`; if absent and exactly one remote exists use it; otherwise the identity is provisional. |
| Q4 | How is the project ID built (DO-004, DM-001)? | `prj_` plus 16 hex characters of SHA-256 over `v1/` and the first strongest evidence at creation. The ID is stored and never recomputed. Later evidence (renamed remote, provider id) is added as aliases that resolve to the same ID. Repositories use `rep_` the same way. Collisions fail loudly with `INDEX_INCONSISTENT`. |
| Q5 | What identity does a repository without a remote get? | The root-commit hash, read through one sanitized read-only Git call (`rev-list --max-parents=0`). If that is unavailable, a provisional identity derived from the real path, flagged for review so a move raises a candidate instead of silently creating a project. |
| Q14 | What makes a project an obsolescence candidate? | Only declared state: lifecycle `deprecated` or `archived` in the canonical profile, or a provider archived flag. Time-based indicators (for example no commits for N days) are opt-in and off by default. An unscanned or inaccessible project is never flagged for that reason. |
| Q15 | Where is a reviewer's decision stored? | In Vyasa's own index as candidate status: open, dismissed, confirmed. This is generated state and never touches a repository. Syncing decisions is a phase 2 question. |

## project-query

| Q | Question | Recommended answer |
|---|---|---|
| Q2 | What are the matching rules? | Name: case-insensitive, matches exact, prefix, or token. Technology: exact normalized key through the registry; no fuzzy or stemmed matching. Several filters combine with AND; several values inside one filter combine with OR unless `match=all`. Text search uses SQLite FTS5 over name, declared purpose, and technology names, with a LIKE fallback. |
| Q5 | What makes projects related (DFR-007)? | Relation types: explicit dependency on another indexed project; profile-declared relation; at least two shared recognized technologies, excluding a ubiquitous list (git, markdown, docker). Ranking is explicit dependency, then profile-declared, then shared-technology count, then name. Counts are integers; no similarity scores. |
| Q6 | Which dependencies are reported (DFR-008)? | Direct dependencies from recognized manifests, with name, constraint, scope (runtime, dev, optional), ecosystem, and source file. A dependency maps to an indexed project when its name equals a package name that project's manifest declares in the same ecosystem. Dependents use the same table in reverse. Transitive dependencies are out of scope. |
| Q12 | Who maintains technology names? | A versioned built-in registry file maps dependency names to technology keys, display names, and categories. An unknown dependency is listed as a dependency and creates no technology. |
